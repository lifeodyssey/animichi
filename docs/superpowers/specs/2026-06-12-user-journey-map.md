# User Journey Map — 巡礼之环

> 产出自 /office-hours,2026-06-12。基于创始人一手证据(D1-D4 问答)+ 两份市场调研
> + Codex 独立冷读。前序输入:2026-04-15 journey spec(已过时,六条 UI 流)、
> 2026-06-12 chat specs(Plan 段)、docs/todo.md critique 遗留。
> 状态:APPROVED(2026-06-12,两轮独立评审 7.5→9/10,六项问题全部修复)

## 0. 旅程的形状:环,不是漏斗(前提 P1)

```
        ┌──────────── 分享物(しおり图 + 免登录公开页)←──────┐
        ↓                                                    │
   発見 Discover ──→ 判断 Decide ──→ 計画 Plan ──→ 歩く Walk ──→ 残す Keep
   (小红书/X 看到)   (值得专程吗)    (chat→路线)   (现场·审判点)  (留念→分享)
        弱              弱             ★强(已spec)      弱·零实现        萌芽
```

获客不靠漏斗顶部投放,靠 Keep 段产出物回流成 Discover 入口(小红书图 / X 卡片)。
环上任何一段断裂,转不起来;**Walk 是审判时刻**(创始人本人在现场弃用,前提 P2)。

## 1. 五段详表

### 段1 発見 Discover — 现状:弱

| | |
|---|---|
| 用户时刻 | 刷小红书/X 看到巡礼帖;看完某部番想"能去吗";已在日本想顺路 |
| 现状 | 首页(已重设计)+ 登录墙;无作品浏览面;分享物不存在,渠道未建 |
| 目标体验 | 看到分享图 → 点进**免登录**公开页 →"我也想去"→ CTA 进 chat |

**断点**:
- **J1** 分享物不存在 → 环的入口缺失(获客引擎未建,P4修订)
- **J2** 落地即登录墙(critique P2)→ 任何外链进来就死(与 P5 直接冲突)
- **J3** 无"人气作品/别人在巡礼什么"浏览面 → 非搜索型访客无事可做

### 段2 判断 Decide — 现状:弱

| | |
|---|---|
| 用户时刻 | "这部作品圣地在哪、有多少、值得专程还是顺路捎?" |
| 现状 | 无页面回答;chat 能答但藏在登录墙后 |
| 目标体验 | 公开作品页:名場面 TOP + 圣地圏分布图 + 示例路线预览 + "排我的路线"CTA |

**断点**:
- **J4** /anime/[id] guide 页已删未重建 → 作品级全景无处看
- **J5** "值不值得"的判断素材(圏分布、代表帧、规模)未成页面——chat spec 的 C3b 圏总览卡可静态复用

### 段3 計画 Plan — 现状:★强(2026-06-12 设计完毕,未实现)

| | |
|---|---|
| 现状 | spec 完整(bd6c847:44 态、SpotPicker、双形态、千点漏斗);chat 页处于删除状态 |
| 残余断点 | **J6** 发送后无流式反馈,用户感知"产品坏了"(根因:流式协议未定案,技术细节见 chat design spec §8)· **J7** 登录边界:chat 可要登录,但路线产物的分享面必须公开(P5)· **J8** 效率回归(/ 快捷键、useRecentRoute,todo 在案) |

### 段4 歩く Walk — 现状:零实现,审判时刻(P2)

| | |
|---|---|
| 用户时刻 | 站在宇治站前,手机四件套:Maps 导航 + 相册动画截图 + Anitabi 网页 + 小红书攻略(D3 实证) |
| 现状 | 仅路线卡预留"歩くモード"位 |
| 目标体验 | 路线卡一键切歩くモード;现场它是唯一要开的 app;每站 = 对照图 + 怎么走 + 打卡 |

**断点(= 四件套的需求翻译)**:
- **J9** 无现场视图:当前站置顶放大、下一站步行指引、剩余时间(Citymapper 范式)
- **J10** 机位对照:动画截图должна在站点卡内,不必翻相册(场景卡已设计,现场态需放大优先)
- **J11** "附近还有什么":替代现场开 Anitabi(search_nearby 后端已有,缺现场 UI)
- **J12** 导航深链:每站"在 Maps 打开"(P3:导航让赢家赢,不重造)
- **J13** 完成感:打卡 checkbox / 进度,产出喂给 Keep
- **J14** 现场环境约束:户外强光对比度(DESIGN.md A11y outdoor 条款)、弱网(static-first 已定)、单手操作
- (长期缺口:小红书的机位经验 UGC 短期无法替代,P3 明示放弃)

**边界**:Walk Mode 假设**单日可完成**的路线;跨城市多日行程(如『氷菓』飛騨
高山两日)的日程拆分属后续范围,本图不设断点。

### 段5 残す Keep — 现状:萌芽

| | |
|---|---|
| 用户时刻 | 走完想发帖/留念;数月后想"上次走到哪了/下次去哪" |
| 现状 | しおり只是路线卡上的一个 CTA 概念 |
| 目标体验 | 走完 → 自动生成しおり页(免登录 URL + OG 竖图)→ 发小红书/X → 新用户点进 → 回到 J2 |

**断点**:
- **J15** 分享物不存在——交付物与 J1 相同(share landing + OG 竖图),但触发
  时机在 Walk 完成后(J1 是消费侧、J15 是产出侧);**两条合并为一张 ticket 实现**
- **J16** 分享物的同行形态未决:结伴巡礼是主流(小红书结队内容是主力),当前
  假设**只读公开 URL**;同行协作查看/打卡同步后置
- **J17** 巡礼记录/历史路线无处存取(todo: history management 悬而未决)
- **J18** 打卡照片×对照帧合成(机位模式延伸,远期)

**全图通则·失败态**:无结果、定位失败、生成失败等降级路径由各段 spec 定义
(Plan 段已有 states spec D 区先例),本图只记正向流。

## 3. 补强优先级(创始人选定 B 主线;旅程图对其内部顺序的修正)

```
1. chat Phase 1(V3 单列流)          ← Plan 兑现,含 J6/J7/J8;路线由此可被创建
2. Walk Mode 最小版(J9-J14)         ← P2:审判时刻优先于桌面增强
3. share landing + OG 竖图 + 公开作品页 ← 一个交付物吃 J1-J5+J15(三段同解)
4. chat Phase 2 双栏 / 历史路线 / 机位模式 / SEO 规模化  ← 环闭合后
```

**旅程图对原 roadmap 的实际修正只有一条**:chat Phase 2(桌面双栏)从"Phase 1 之后
立刻做"降级为"环闭合后做"——Walk Mode 和分享落地面插队。依据:P2 + 创始人现场
弃用实证 + Codex 独立同构建议。

## 4. 前提与证据记录

- P1 环形旅程 / P2 Walk 审判点 / P3 四件套只赢三件 / P5 登录墙后移 — 创始人确认
- P4(修订版):Keep 产出物 = 免登录公开分享页 + 自动 OG 竖图,同一资产喂两渠道
  (图→小红书、卡片→X);时序上 Walk 先于 Keep;大规模 SEO 后置。
  修订源于 Codex 挑战("分享依赖先有高质量 Walk;公开页长尾被低估")+ 我方反驳
  ("小红书外链敌意,图片导出不可省")的合成
- 证据链:D1 认真做产品自己是用户 / D2"查过点位,现场用的是别的"/ D3 现场四件套
  全勾 / D4 双 persona(中文圈小红书 + 日本圈 X)
- Codex 冷读钢人化:"动漫圣地巡礼的**现场作战系统**"——比"AI 旅行规划器"更准的自我定义

## 5. 环转起来的判据(可测)

1. **Dogfood 判据**:创始人下一次巡礼,全程只开自己的产品(四件套 → 一件)
2. **第二用户判据**:≥1 个朋友独立走完一条路线并主动发出分享物
3. **回流判据**:从分享物链接进来的新会话 > 0(环的第一圈)
