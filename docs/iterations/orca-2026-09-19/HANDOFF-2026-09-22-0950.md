## Merges are strictly serial here, and that is the throughput ceiling

The repo requires branches to be up to date with `main`, and this is a personal-account repo with
no merge queue (`reference_merge_queue_personal_repo`). So **every merge makes every other open PR
`BEHIND`**, each needing `gh pr update-branch` and a full CI re-run. All seven open PRs were
`BEHIND` at tick start for exactly this reason. Plan one merge per tick and start the next PR's
branch update immediately after, so its CI runs during the next tick's other work.

**The merge guard is a PreToolUse hook and its criterion is not the one you would guess.**
`~/.claude/hooks/check-pr-comments.sh` blocks the merge command when
`bots_saw_head == 0 && head_age < 600`. It compares the **head commit's timestamp** against the
**newest bot comment's timestamp**. I first treated "the CodeRabbit pending check disappeared" as
proof the bots had reviewed; they had not. A pending check clearing says the check ended, not that
a review landed — `feedback_proxy_signal_not_evidence`. Wait out the 600s window and retry; do not
try to satisfy it by re-reading check state.

Two more things about that hook, both of which cost me a round trip:

- The merge CLI prints **nothing at all** on success. Verify against
  `gh api repos/…/commits/main`, never against the command's silence.
- The hook is **fail-closed on its own parser**. Writing a handoff file whose *prose* contained the
  merge command's name, via a heredoc, was blocked with "could not parse the merge command well
  enough". Use a file-writing tool rather than a shell heredoc for any document that quotes it.

- the fix is a writer lane that re-pins `PGVECTOR_APT_VERSION`, and the card should ask *why the
